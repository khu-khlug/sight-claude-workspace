# Frontend Task 문서 작성 Standard

## 목적

Frontend Task 문서는 작업으로 달성할 사용자 목표, 사용자에게 관찰되는 경험, 허용하거나 제한할 행동과 그 보장 방법을 사람이 구현 전에 검토할 수 있도록 설명한다.

사람은 다음 내용을 검토한다.

- 대상 사용자와 사용 목적
- 사용자가 목표를 달성하는 흐름과 결과
- 사용자에게 허용하거나 금지하는 행동과 예외
- 입력 실패, 중단 및 재시도 시 복구 경험
- Backend와 외부 시스템에 의존하는 사용자 경험
- 개인정보, 비가역적 행동 및 사용자 보호
- 접근성 및 사용 환경

component, hook, store, CSS와 내부 파일 구성 등 사용자에게 관찰되지 않는 구현은 Task에서 결정하지 않는다. 반복되는 사용자 인터페이스 원칙은 프론트엔드 공통 규칙으로 관리하고, Task에는 해당 작업에서 달라지는 경험과 정책만 작성한다.

## 저장 위치와 상태

- Frontend Task 문서는 문서 시작의 YAML frontmatter에 `type: frontend`를 단일 값으로 선언한다.
- 완료되지 않은 Task 문서는 `tasks/open/`에 둔다.
- 완료된 Task 문서는 `tasks/completed/`로 옮긴다.
- `tasks/_schema/frontend.yaml`은 Task 문서의 필수 입력, 섹션 순서와 구조화된 정책 형식을 정의한다.

## 작성 원칙

### 사용자에게 관찰되는 계약을 작성한다

다음 내용을 사용자의 관점에서 작성한다.

- 어떤 사용자가 어떤 상황에서 기능을 시작하는가
- 사용자가 어떤 목표를 달성할 수 있는가
- 어떤 상태와 결과를 구분할 수 있어야 하는가
- 어떤 행동이 허용되거나 금지되는가
- 실패하거나 중단된 뒤 무엇을 할 수 있는가

정확한 URL, 외부에 표시되는 상태 이름, 정책상 고정된 문구와 개인정보 표시 형식처럼 사용자 또는 외부 시스템이 관찰하는 identifier는 정확하게 작성한다.

### 공통 원칙을 반복하지 않는다

일반적인 loading, empty, error, retry 및 feedback 원칙은 프론트엔드 공통 규칙을 따른다. Task에는 도메인 상태에 따라 가능한 행동, 결과의 의미 또는 회복 방법이 달라지는 경우만 `사용자 경험 계약`에 작성한다.

### 확정된 정책을 작성한다

Frontend Task는 구현 전에 합의된 사용자 경험과 정책을 기록한다. 사용자 경험 또는 허용 범위를 바꾸는 미결정 사항이 남아 있으면 이를 확정한 뒤 Task에 반영한다.

## 입력 작성 지침

Task 문서는 `tasks/_schema/frontend.yaml`에 정의된 섹션을 같은 이름과 순서로 작성한다. 필수 여부와 구조화된 입력 형식은 YAML schema를 기준으로 한다.

### 1. 작업 개요

- 해결하려는 문제 또는 제공하려는 기능
- 변경되는 사용자 경험의 범위
- 완료 여부를 판단할 수 있는 결과

### 2. 사용자와 목표

- 대상 사용자 또는 사용자 집단
- 기능을 사용하는 맥락과 시작 조건
- 사용자가 달성하려는 목표
- 사용자가 기대하는 완료 결과

### 3. 사용자 경험 계약

- 사용자가 기능에 진입하는 방법과 진입 전제 조건
- 목표를 달성하는 주요 흐름
- 사용자에게 구분되어야 하는 도메인 상태와 각 상태에서 가능한 행동
- 성공, 부분 성공 및 실패 결과의 의미
- 완료, 취소 및 이탈 뒤 이동하거나 유지되는 상태
- 작업 중단 또는 외부 상태 변경 뒤 다시 진입했을 때의 경험
- 기존 URL, bookmark, browser history 또는 사용자 흐름을 변경할 때 유지할 경험

일반적인 component 구성, layout, loading 표시 방식과 공통 오류 표현은 작성하지 않는다.

### 4. 허용 및 제한 정책

작업으로 사용자 행동의 허용 범위 또는 제한 방식이 달라지지 않으면 `정책 변경 없음`만 작성한다.

정책이 있으면 정책마다 `###` 제목을 작성하고 다음 field를 schema 순서대로 정확히 한 번 작성한다. field는 `- 이름: 값` 형식의 한 줄 목록 항목으로 작성하며 값은 비워 둘 수 없다.

- `주체`: 정책이 적용되는 사용자 또는 사용자 집단
- `조건`: 정책을 판단하는 시점의 상태와 전제 조건
- `행동`: 사용자가 시도하거나 수행하는 행동
- `판정`: `허용`, `금지`, `조건부 허용` 중 하나
- `허용 예외`: 기본 판정과 다르게 허용하는 조건. 예외가 없으면 `없음`
- `사용자에게 보이는 처리`: 노출하지 않음, 비활성화, 실행 차단, 확인 후 진행, 다른 흐름으로 이동 등 사용자가 관찰하는 처리
- `보장 계층`: 사용자 인터페이스 동작만으로 충분하면 `Frontend`, 권한 또는 비즈니스 규칙을 서버에서도 강제해야 하면 `Frontend와 Backend`
- `안내 및 회복`: 판정 이유를 어떻게 이해하고, 허용 상태로 전환하거나 다른 행동을 선택할 수 있는지 설명. 가능한 회복 방법이 없으면 `없음`

권한, 개인정보 접근, 비용 발생, 데이터 변경과 비가역적 행동은 화면에서 숨기거나 비활성화하는 것만으로 보장하지 않는다. 해당 정책의 `보장 계층`을 `Frontend와 Backend`로 작성하고 관련 Backend Task 또는 기존 Backend 계약을 `데이터 및 연동`에서 참조한다.

```markdown
## 허용 및 제한 정책

### 처리 중인 요청의 중복 실행

- 주체: 변경 권한이 있는 사용자
- 조건: 이전 변경 요청의 결과가 아직 확정되지 않음
- 행동: 같은 변경을 다시 요청
- 판정: 금지
- 허용 예외: 없음
- 사용자에게 보이는 처리: 실행할 수 없게 하고 이전 요청이 처리 중임을 표시한다.
- 보장 계층: Frontend와 Backend
- 안내 및 회복: 이전 요청 결과가 확정되면 다시 실행할 수 있다.
```

### 5. 입력 및 복구

- 허용하는 입력과 거부하는 입력의 의미
- 검증 결과를 사용자에게 알리는 시점
- 실패 또는 재시도 시 보존하거나 초기화하는 입력
- 변경 중 이탈하거나 취소할 때의 처리
- 중복 제출과 연속 실행의 의미
- 자동 저장, 임시 저장 또는 작성 내용 복구가 필요한 조건

해당 작업에서 공통 입력 원칙 외에 달라지는 내용이 없으면 `변경 없음`을 작성한다.

### 6. 데이터 및 연동

- 화면에 필요한 데이터와 각 데이터의 사용자 관점 의미
- 데이터의 source of truth
- 사용자 경험이 의존하는 Backend Task, API 또는 외부 시스템
- 데이터 최신성이 중요한 조건과 갱신 결과
- 일부 데이터만 제공되거나 연동에 실패했을 때 허용할 행동
- Frontend와 Backend의 배포 또는 제공 순서
- 단계적 공개, feature flag 또는 기존 화면과 함께 제공하는 동안의 동작

HTTP field와 내부 요청 구현을 중복 설계하지 않고 관련 Backend Task 또는 확정된 API 계약을 참조한다. 해당 작업에 연동 변경이 없으면 `변경 없음`을 작성한다.

### 7. 사용자 보호 및 개인정보

- 조회, 입력 또는 표시하는 개인정보와 민감정보
- 마스킹, 복사, 브라우저 저장 및 URL 포함 여부
- 권한이 없는 사용자에게 노출될 수 있는 정보
- 비가역적 행동, 비용 발생 또는 외부 알림 전 확인할 내용
- 의도하지 않은 중복 행동이나 데이터 손실을 막는 조건

해당 작업에서 달라지는 내용이 없으면 `변경 없음`을 작성한다.

### 8. 접근성 및 사용 환경

- 작업 고유의 keyboard, focus 및 screen reader 경험
- 색상, 아이콘 또는 시각적 위치만으로 전달해서는 안 되는 정보
- 모바일, 좁은 화면 또는 긴 content에서 유지해야 하는 사용성
- 지원 환경에 따라 기능을 제한하는 경우의 대체 경험

공통 접근성 및 반응형 원칙만 적용되면 `공통 원칙을 따름`을 작성한다.

### 9. 검증

- 대상 사용자별 주요 성공 흐름
- 허용, 금지 및 조건부 허용 정책
- 도메인 상태별 가능한 행동과 결과
- 입력 경계값, 실패 후 복구와 중복 실행
- 개인정보 및 비가역적 행동의 보호
- Backend 또는 외부 시스템의 실패와 부분 성공
- 접근성 및 지원 사용 환경
- 변경 대상에 포함된 기존 URL과 사용자 흐름

각 항목은 사용자가 관찰할 수 있는 기대 결과와 검증 방법을 작성한다.

### 10. 비목표

이번 작업에서 제공하지 않는 사용자 경험과 다루지 않는 인접 기능을 작성한다. 비목표가 없으면 `없음`을 작성한다.

## Task 문서, schema, 공통 규칙 및 lint의 역할

- Task 문서는 이번 작업에서 달라지는 사용자 경험, 정책과 검증 경계를 기록한다.
- YAML schema는 필수 입력, 섹션 순서와 구조화된 정책 형식을 정의한다.
- 프론트엔드 공통 규칙은 여러 작업에 반복 적용할 loading, error, accessibility 및 구현 가드레일을 정의한다.
- lint는 schema에 따라 필수 내용과 정책 field의 구조를 deterministic하게 검사한다.
- 사람은 사용자 목표, 정책의 의미, 예외 및 사용자에게 보이는 처리가 적절한지 검토한다.
